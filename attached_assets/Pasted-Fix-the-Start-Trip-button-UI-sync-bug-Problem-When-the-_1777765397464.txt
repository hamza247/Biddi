Fix the “Start Trip” button UI sync bug.

Problem:
When the driver/user taps the Start Trip button, the backend seems to update correctly, because after killing and reopening the app the screen shows “Trip Started”. But immediately after tapping Start Trip, the current screen does not update. This means the app state/UI is not syncing after the action.

Goal:
After tapping Start Trip, the UI should immediately change to the correct trip-started state without needing to restart the app.

Important:
- Do NOT rebuild the app.
- Do NOT fake the UI state only.
- Fix the real sync issue between API response, local state, cache, socket events, and navigation.
- Keep existing booking/trip flow working.

Step 1 — Find the Start Trip flow

Search the codebase for:
- Start Trip
- startTrip
- start_trip
- trip started
- begin trip
- ride started
- eTripStatus
- tripStatus
- bookingStatus
- rideStatus

- handleStartTrip

Find:
- Start Trip button component

- Backend route/controller
- Current trip screen/state
- Trip/booking status enum values
- React Query/cache/state management if used
- Socket.IO events if used
- Navigation logic after trip status changes

Step 2 — Confirm backend update

Inspect the API response after Start Trip.

Check:
- Does the API return success?
- Does it return updated trip object?
- Does it return the new status?
- Is the frontend ignoring the response?
- Is the frontend checking the wrong status value?
- Is the backend returning a different field name than frontend expects?

Expected response should include something like:

{
  "success": true,
  "trip": {
    "id": "...",
    "status": "started"
  }
}

If the backend updates the database but does not return the updated trip, fix it to return the updated trip/booking data.

Step 3 — Fix frontend state update

After Start Trip succeeds, update the current screen state immediately.

Depending on the app architecture, do one or more of these:

- Update local trip state
- Update React Query cache
- Refetch current trip
- Invalidate trip query
- Update Redux/Zustand/context store if used
- Navigate/replace to the correct active trip screen
- Trigger status step update
- Recalculate button visibility

Do not require app restart.

Example logic:

1. User taps Start Trip
2. Disable button and show loading
3. Call Start Trip API
4. On success:
   - Save returned updated trip
   - Update selected/current trip state
   - Invalidate/refetch active trip query
   - Emit/listen to socket update if used
   - Change UI to Trip Started state
5. On error:
   - Re-enable button
   - Show error message

Normalize status using a helper:

normalizeTripStatus(status)

Map all backend values to stable frontend statuses:

Use normalized status for:

Step 5 — Fix stale cache issue

Since restart shows correct state, this is likely stale app state/cache.

Check for:
- React Query query not invalidated
- AsyncStorage holding old trip state
- Redux/Zustand store not updated
- component state initialized once and never refreshed
- navigation params holding old trip object
- screen not listening to focus/refetch
- socket event not updating current trip
- optimistic update missing
- wrong dependency array in useEffect
- memoized trip status not recalculating

Fix properly.

If React Query is used:
- invalidateQueries for current trip
- invalidateQueries for active booking/trip
- updateQueryData with returned trip
- refetch after mutation success

If navigation params are used:
- replace stale params with updated trip
- or fetch fresh trip by id instead of relying only on params

If AsyncStorage is used:
- update stored active trip after success
- avoid reading stale stored trip over fresh API data

Frontend should update UI when receiving this event.
