Build a modern mobile ride-hailing app called Biddi with a Node.js backend and PostgreSQL database.

IMPORTANT PRODUCT RULES:
1. This is ONE app for both customers and drivers.
2. Default app mode is Rider.
3. Inside the rider app there must be a "Become a Driver" button.
4. If the user completes driver onboarding and is approved, the same account can switch between Rider Mode and Driver Mode from profile/settings.
5. For now, ONLY support the bidding ride request concept.
6. Do NOT build rentals, delivery, airport, pets, pool, corporate, later booking, wallet marketplace, or other service categories.
7. Keep the UI very smooth, modern, and minimal.
8. Requesting a ride must take only 1 or 2 taps after pickup/destination are known.
9. Keep the design evolution close to the existing app style: purple branding, map-based screens, bottom sheets, simple cards. Do not redesign 180 degrees.

TECH STACK:
- Mobile app: React Native with Expo
- Backend: Node.js + Express + TypeScript
- Database: PostgreSQL
- ORM: Prisma
- Authentication: OTP phone login
- Realtime: Socket.IO
- Maps: Google Maps or Mapbox
- State management: Zustand or React Query
- Admin panel: simple web admin in Next.js or React
- File uploads: Cloudinary or S3-compatible storage

CORE APP CONCEPT:
This app is a ride bidding app similar to inDrive:
- Rider enters destination
- Rider confirms ride request
- Nearby drivers receive the ride request
- Drivers submit bids (price offers)
- Rider sees incoming bids in real time
- Rider accepts one bid
- Trip starts
- Trip ends
- Payment is marked as cash for v1
- Ratings after trip

UX / UI RULES:
- Very few buttons
- One primary action per screen
- Large tap targets
- Simple typography
- Bottom sheet based ride flow
- Keep purple as primary brand color
- Minimal steps and minimal clutter
- Avoid feature overload
- Do not show many ride categories
- Focus on speed, clarity, trust, and ease

APP MODES:
A) Rider Mode
B) Driver Mode

ACCOUNT MODEL:
Use one account per person.
A user can have:
- rider profile
- optional driver profile
- app_mode = rider or driver
- driver_status = not_applied / pending / approved / rejected / suspended

MAIN USER FLOWS:

RIDER FLOW:
1. Login with phone OTP
2. Home screen opens in Rider Mode
3. Show pickup field (default current location)
4. Show destination search
5. Show one main CTA: "Request Ride"
6. After tapping Request Ride, create a ride request and broadcast it to nearby approved drivers
7. Rider enters bid collection screen
8. Rider sees incoming driver bids in real time
9. Rider selects a bid
10. Assigned driver screen opens
11. Live trip tracking
12. Trip complete
13. Rider can rate driver

DRIVER FLOW:
1. User taps "Become a Driver"
2. Driver onboarding form
3. Upload documents
4. Add vehicle
5. Admin approval required
6. Once approved, user can switch app mode to Driver
7. Driver home screen has online/offline toggle
8. While online, driver receives nearby bidding ride requests
9. Driver can place a bid amount
10. If rider accepts the bid, trip is assigned
11. Driver navigates to pickup
12. Start trip
13. End trip
14. Driver can see earnings summary

BIDDING RULES:
- Rider creates a ride request with pickup, dropoff, estimated distance, estimated duration
- Nearby online drivers within configurable radius receive the request
- Drivers can submit one bid amount
- Rider receives bids in realtime
- Rider can accept one bid
- Other bids automatically expire or become rejected
- Once accepted, create a trip record
- Track trip status transitions:
  requested -> bidding -> driver_selected -> driver_arriving -> arrived -> in_progress -> completed
  also support cancelled_by_rider / cancelled_by_driver / expired
